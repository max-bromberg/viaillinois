# How VIA is found

VIA is a single page application. The server sent one empty document for every
address and the browser built the page from it, which is fine for a person and
close to useless for a search engine. Every address returned the same title,
the same description and an empty body, nothing linked to an event page in the
HTML, and the sitemap listed four fixed pages using relative addresses that the
sitemap protocol does not accept. That is why the site ranked only for its own
name and why individual event pages never appeared at all.

## What the server now sends

`server/middleware/htmlShell.js` fills the built `index.html` in before sending
it. For each address, `server/services/seoPages.js` supplies:

- a title and description written for that page
- a canonical address, taken from `CLIENT_URL` rather than the request host, so
  a spoofed `Host` header cannot put another domain into a canonical tag
- sharing tags, including a PNG card, because no social platform renders SVG
- schema.org structured data as JSON-LD
- a readable summary of the page in the body

The application removes that summary when it starts, in `client/src/main.js`,
and renders the same content properly. A crawler and a person see the same
thing, which is the difference between progressive enhancement and cloaking.

Everything written into the document is escaped. Event titles, descriptions and
locations are written by RSO admins and imported from calendar files, so all of
it is untrusted by the time it reaches the HTML.

## Structured data

`server/lib/seo/structuredData.js` produces:

- `Event` on each event page, with start and end times carrying the campus
  timezone offset, the organizing RSO, and either a `Place` with the room and
  the campus locality or a `VirtualLocation` when the location names a video
  call. Google needs this to show an event with its date and place rather than
  as a bare link, and assistants read it instead of rendering the page.
- `ItemList` of upcoming events on the front page.
- `WebSite` with a `SearchAction`, and `Organization`, on the front page.

Times are stored as wall clock because that is what the organizer typed. Any
time published for a machine goes through `server/lib/timezone.js`, which adds
the offset. Without it the value is ambiguous by an hour twice a year and six
hours out to anything that assumes UTC.

## Sitemap and robots

Both are generated by `server/routes/seo.js` rather than shipped as static
files, and are registered before the static handler so the generated ones win.

The sitemap lists every public event, using `getPublicEventSitemapEntries`
rather than the feed query, which paginates at twenty. Internal events are
excluded from the sitemap and carry `noindex`.

`robots.txt` names the crawlers behind assistants explicitly, because several
of them only index a site that says so. `llms.txt` describes the site in the
form those assistants look for: what it is, which pages exist, and where the
machine readable parts live.

## Keeping it working

- New public routes need an entry in `seoPages.js`, or they are served with a
  `noindex` default.
- Anything that should not be indexed goes in `PRIVATE_PATHS`.
- The sharing card is generated by `node scripts/make-og-card.mjs`. Run it when
  the branding changes.
- After deploying, submit `https://viaillinois.com/sitemap.xml` in Google
  Search Console. Nothing here makes that unnecessary, and until the sitemap is
  submitted the event pages are found only by crawling the front page.
